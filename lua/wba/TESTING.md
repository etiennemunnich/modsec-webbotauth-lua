# Testing

"Tested" here means: every layer is checked against something other than this code's own output. Signatures are made by openssl, WebCrypto or the reference signer, never by the verifier; parsers run against the standards' own corpora and examples; and the whole plugin runs inside a real CRS nginx container, where every outcome ModSecurity logs is asserted. The tests validate outcomes: which status and reason a request gets, which rule refused it, what was logged. Timing is never a test result; a few generous ceilings exist only to catch a path that grows out of proportion ([Budgets the tests enforce](#budgets-the-tests-enforce)).

Every count on this page is from one run on 2026-10-12, on Finch on macOS (Apple silicon), on the base image the `Dockerfile` pins (`owasp/modsecurity-crs:4.30.0-nginx-202610051210`: ModSecurity 3.0.17, CRS 4.30.0). Docker (`DOCKER=docker`) last ran the full set on 2026-10-10, on an earlier build of this plugin.

## Run the tests

```bash
lua/tests/run_all.sh              # Lua suites, corpora, vectors, planted bugs, fixture freshness, key-sync, issue forms
JOBS=2 lua/tests/run_all.sh       # the same, planted bugs in two shards at once
lua/tests/run_all.sh --live       # plus the image test stage, the live suite, the README Quick start, the registry path,
                                  # the real-IP checks, the bot lists path, GETTING-STARTED.md on Debian 13 and the go-ftw tests (Finch)
DOCKER=docker lua/tests/run_all.sh --live        # the same on Docker
DOCKER="sudo finch" lua/tests/run_all.sh --live  # on Linux, where Finch runs as root

# Not in run_all.sh (CI's live job still runs paranoia.sh and ftw-planted.sh;
# getting-started.sh is in CI on Docker only; see Continuous integration):
bash lua/tests/live/paranoia.sh      # CRS paranoia levels 1 to 4, HTTP/1.1 and HTTP/2
bash lua/tests/live/matrix.sh        # the live suite on every image in lua/tests/live/crs-images.txt
bash lua/tests/live/ftw-planted.sh   # eight bugs planted in a copy; each go-ftw test must catch its own
bash lua/tests/live/pcre-limit.sh    # ModSecurity's regular-expression work limit on the Debian setup
bash lua/tests/live/collections-probe.sh   # why replay counts are files, not ModSecurity collections
lua/tests/interop/interop.sh         # against the latest draft vectors, npm web-bot-auth and Stytch's recipe (not hermetic)
lua lua/tests/coding/bench.lua       # what each decoding path costs; a measurement, not a test
```

Run the live scripts with `bash`, not `sh`. Each container script takes its CLI from `DOCKER` (Finch by default, `docker` for Docker) and removes the images it built when it ends.

What each part needs:

- **Lua suites:** `lua` 5.3 or later and `openssl` 3.x on `PATH`.
- **Key sync and fixture freshness:** Bun and Node. A missing tool is reported as SKIP, never as a pass.
- **Live:** a container CLI, `curl` with HTTP/2, Bun or Node (`h2.ts`, the test bots); for `--live` also network access from the container (Debian mirrors, GitHub, coreruleset.org, for the Debian guide) and go-ftw 2.x (`brew install coreruleset/tap/go-ftw`; `FTW=/path/to/go-ftw` to choose one).
- **`test_crypto`, the Wycheproof vectors and `crypto.lua`'s planted bugs** need lua-openssl, so they run in the image's test stage (`finch build -f lua/wba/Dockerfile --target test .`), which `run.sh` builds first.

`run_all.sh` prints one line per step (`OK`, `FAIL`, `SKIP`) and exits non-zero if any step failed. `run.sh` counts its own passes and fails unless exactly `EXPECTED_PASSES` (231) were printed, so a check that quietly did not run fails the suite.

## Continuous integration

Five workflows in `.github/workflows/` run the same scripts on GitHub's Ubuntu runners. `wba.yml` runs on every push and pull request that changes more than documents: a `suites` job (`run_all.sh` on Lua 5.3, planted bugs in two shards, then the Lua suites on 5.4, under a Latin-1 locale) and a `live` job on Finch and again on Docker (`run.sh`, the Quick start, the real-IP checks, the go-ftw tests, `ftw-planted.sh`, the registry and bot-lists paths, the paranoia levels, and on Docker only `getting-started.sh` for [GETTING-STARTED.md](GETTING-STARTED.md)). Guide-only edits to that page still start `wba` (it is not in `paths-ignore`). `security.yml` runs ASH (Bandit, Semgrep, Checkov, detect-secrets) on every push; a finding at MEDIUM or above fails unless `.ash/.ash.yaml` suppresses it with a reason. `lint-workflows.yml` runs actionlint and zizmor when `.github/` changes. `crs-matrix.yml` runs the version matrix monthly, when the image list or the `Dockerfile` changes, or by hand. `interop.yml` runs by hand.

## Checked against outside sources

- The draft's own Appendix E.1.1 and E.1.2 (`rsa-pss-sha512`) and E.2.1 and E.2.2 (`ed25519`) vectors verify, end to end.
- RFC 9421 B.2.1 to B.2.3 (`rsa-pss-sha512`), B.2.4 (`ecdsa-p256-sha256`) and B.2.6 (`ed25519`) verify over the bases built here; RSA-PSS and ECDSA signatures are randomized, so that holds only for a byte-exact base.
- The fresh-key tests sign with openssl over hand-written signature bases, for every algorithm, and openssl is the verifier on the host: it re-encodes ECDSA signatures and builds RSA and EC public keys itself (`asn1parse`), never with this code.
- `wba-keysync` reproduces the RFC 8037 A.3 and RFC 7638 3.1 thumbprints and the draft's E.1 and E.2 keyids; the EC and RSA fixture thumbprints are computed by openssl.
- The draft's Appendix E.2.3 signed directory response validates as a possession proof; the proof tests otherwise sign hand-written bases with the runtime's WebCrypto, never with this code.
- SHA-256 matches the FIPS 180-4 examples and openssl for every length from 0 to 1000 bytes, and so does lua-openssl's SHA-512; digest checks use the RFC 9421 and RFC 9530 example digests.
- Content codings: `coding.lua` agrees, byte for byte, with zlib (Node's, and again Bun's) on 2895 inputs ([`test_coding`](#lua-unit-suites)); RFC 9530 Figure 2 and the unencoded-digest draft's Figure 2 decode to their published digests.
- Conformance corpora: the HTTP Working Group's RFC 9651 corpus (2137 records; key-sync's own parser runs its 1593 parse records), every RFC 9421 component example for the supported request forms, 2720 `@query-param` vectors against WHATWG `URLSearchParams`, the 17 draft-00 negative vectors, and 100 identifier vectors that the Lua and TypeScript implementations must both reproduce ([Standards conformance](CONFORMANCE.md#summary-by-standard)).
- Crypto: 1798 [Wycheproof](https://github.com/C2SP/wycheproof) vectors agree with `crypto.lua` over the exact lua-openssl build the image ships, 0 disagreements ([Crypto: Wycheproof](#crypto-wycheproof)).
- The latest upstream, on demand: `interop.sh` runs the draft's current request test vectors (the editor's copy, through `verify.lua` with openssl doing the crypto), installs the latest `web-bot-auth` from npm (Cloudflare's reference signer) and sends signed requests from it, and runs Stytch's example recipe; it names the upstream versions it used and reports a change to Stytch's file for review. Operators run the same script against their own WAF (README, "Check your deployment against the latest upstream").

## Conformance suites

- **`test_sf_corpus`:** every record of httpwg/structured-field-tests (`sf-corpus/`, pinned by commit and a `MANIFEST` of SHA-256 hashes the suite checks first). Parse records must parse to `expected` (or fail when `must_fail`), and `expected` must serialize to `canonical`; serialization records must serialize or fail as marked. The corpus tells Integers from Decimals by JSON literal (`1` against `1.0`), which JavaScript's `JSON.parse` erases, so the files are read by a small test-only Lua JSON reader.
- **`test_components`:** each component example in RFC 9421 2.1 and 2.2 as a signature-base line, byte for byte; the URL Standard's decoding rules (`+`, stray `%`, U+FFFD replacement by maximal subpart); and 2720 `@query-param` vectors from `query-param/gen.ts`, decided by the runtime's own `URLSearchParams` (Bun and Node agree). `@query-param` with any parameter besides `name` is `unsupported-component` (2.2.8 defines only `name`).
- **`test_negative_vectors`:** each vector's request, body, clock and key, with the test key allowed and the window cap off (the draft's E.2 parameters, as in `test_verify`), run as phase 2 sees it (body available), so the outcome is the final one. A vector must reach its outcome for its intended reason: with the window cap left on, all of them would be `invalid` for the wrong reason, and the suite says so. 16 of the 17 match as written. NV-10 expects RFC 9651 4.2's "malformed" branch, which `tx.wba_malformed=reject` gives (checked); the default ignores the field.

## Lua unit suites

openssl signs, verifies and makes every encoding the tests need (RSA and EC SubjectPublicKeyInfo, ECDSA r ‖ s to and from DER, with `asn1parse`), so the verifier is never checked against a signature or encoding this code produced (`helpers.lua`). Checks per suite: `test_base64` 4, `test_structured_fields` 10, `test_sf_corpus` 2, `test_components` 9, `test_sigbase` 7, `test_keys` 8, `test_sha256` 3 (4 in the image), `test_coding` 7, `test_replay` 4, `test_verify` 55, `test_negative_vectors` 2, `test_entry` 19 (20 in the image), `test_log` 7, `test_conf` 5, `test_crypto` 5 (image only). One check often covers many cases.

- **`test_base64`:** RFC 4648 vectors, every byte value round-tripped, and RFC 9651 4.2.7's tolerance of missing or partial padding and non-zero pad bits.
- **`test_structured_fields`:** typed parsing, and byte-exact re-serialization of the draft's E.2.1 `Signature-Input`, including `;key=` and a quoted `nonce`. 23 malformed inputs that must raise: control bytes, hex and exponent "integers", decimals, duplicates. Display Strings reach each UTF-8 guard the corpus does not: an overlong E0 form, F4 above U+10FFFF and a third byte that is not a continuation byte are refused; U+40000 and U+10FFFF parse and re-serialize.
- **`test_sigbase`:** the RFC 9421 B.2.6 base and both draft E.2 bases rebuilt byte for byte, with each published signature verifying over the rebuilt base. RFC 9421 B.2.1 to B.2.4 and the draft's E.1.1 and E.1.2 verify over the bases built here; those signatures are randomized, so only a byte-exact base passes. The vectors are in `rfc_vectors.lua`, copied from the documents with RFC 8792 wrapping undone. The memo of a parsed field is checked by counting searches over the text (`H.searches` in `helpers.lua`), not by timing.
- **`test_sha256`:** the FIPS 180-4 example vectors (empty, `abc`, the 448- and 896-bit messages, one million `a`), RFC 9421 7.2.8's digest, and openssl for every message length from 0 to 1000 bytes, which crosses every padding boundary. In the image test stage, `crypto.lua`'s SHA-512 (lua-openssl) gets the same comparison.
- **`test_coding`:** `coding.lua`, the content codings.
  - Every line of `coding/vectors.tsv` (2895), each decoded and compared with what zlib did with it: the same refusal, or the same bytes (length and SHA-256). The file holds zlib's own output for eight inputs over levels 0, 1, 6 and 9, four strategies, window sizes 9 and 12 and memLevel 1 (raw, zlib and gzip); three streams flushed after each of 40 writes; 46 hand-built streams for each RFC 1951 error and each edge zlib accepts; zlib and gzip header and trailer errors, wrong wrappers and both RFC figures; every truncation and every single-bit flip of five small streams; and 700 random inputs.
  - The RFCs' figures by their published digests; RFC 1952 members and RFC 1950 single streams, where zlib-based tools differ from the text (trailing bytes are refused); stacked codings; FDICT, which RFC 1950 2.3 forbids where no dictionary is defined, as corrupt; unknown codings; LEN 65535 and a match 32768 back into stored bytes.
  - The budget to the unit, for a fixed and a dynamic block. A 10 MiB gzip bomb and the same gzipped again, 8193 empty fixed and stored blocks, 129 empty dynamic blocks, 140000 literals on 15-bit codes, and a 1 MiB FCOMMENT under FHCRC each stop at the default budget. The floods, the 15-bit literals and the header also decode with no budget, so the budget is what stopped them.
  - Every prefix of a gzip stream with a dynamic block (the gzip CLI's `-9` over 4000 random letters) is `corrupt`, and none raises.
- **`test_keys`:** the key-store contract (format version 2).
  - `fixtures/wba-keys.tsv` is the exact file `wba-keysync` emits; its test asserts the same bytes. It holds Ed25519, P-256, P-384 and RSA keys, with and without an `alg` pin, every proof state (`valid`, `invalid`, `none`) and a `jwks_uri` identifier on an IPv6 literal. The EC and RSA keys were generated by openssl for it (private halves discarded), and openssl recomputes each keyid as its RFC 7638 thumbprint.
  - Every row of `fixtures/identifiers.tsv`: a request's directory member (strict), an operator's origin, and `jwks_uri` and `cimd` URLs; every identifier returned is its own normal form.
  - Every malformed store rejected whole, 36 cases: key types, `alg` names for another type, `hmac-sha256` and JOSE names, compressed or wrong-curve points, RSA `n` and `e` that are not minimal, even, too short, too long or too large; a proof that is not `valid`, `invalid` or `none`, a `valid` without its expiry, an expiry on another state; identifiers with a query or an IPv6 literal not in RFC 5952 form.
  - RSA bounds against keys openssl makes: 2047 and 1024 bits refused, 2048 accepted; and the edges, 16384 bits, e = 3, a 256-bit e. A version 1 store still loads: every key Ed25519, no `alg`, proof `none`.
  - The per-bot index is checked by counting searches over the file (`H.searches`), not by timing: a lookup reads only the bot a signature names.
- **`test_verify`:** the state machine.
  - Both draft vectors verify. Freshness, `alg` and `keyid` checks. Coverage rules; attribution cannot be moved to another agent. Signature-Agent URL and type rules; component rules. Key-store and crypto failure modes.
  - Several signatures on one request, including the draft's Appendix D.2 shape: an outer signer that also covers the inner signer's member is attributed to its own member, never the inner one.
  - Lowercasing touches only A-Z, including under a Latin-1 locale where `string.lower` maps byte 0xC0 to 0xE0.
  - Body digests (RFC 9530), with the RFCs' own example digests: phase 1 pends, a matching body verifies, an added or removed byte is `invalid/digest-mismatch`; the strongest covered algorithm decides; an appended, uncovered member cannot vouch for a swapped body; Deprecated and unknown algorithms are ignored; malformed fields are `invalid` without the body; incomplete and oversized bodies are `unverified`; a pending signature outranks an invalid one; the body is read only after a good signature, and each algorithm runs once per request.
  - Partial content (RFC 9530 3, RFC 9110 14.4 and 14.5): `Content-Range` on POST and PATCH is ignored and the digest verifies; a PUT verifies only when its range is the whole representation (in any letter case) and the content has that length; nine other ranges, an Unencoded-Digest on a partial PUT, and a range claiming 40 bytes over 18 are `unverified/digest-partial`.
  - Unencoded-Digest over coded bodies (draft-ietf-httpbis-unencoded-digest-05): the draft's Figure 2 gzip request verifies with its sha-256 and sha-512 Unencoded-Digest and, together, its Repr-Digest over the coded bytes; unknown member parameters are ignored; `x-gzip`, letter case, `identity`, empty list elements, `deflate` and `deflate, gzip` stacked all verify; the wrong order, a body that is not its coding, a truncated stream, a trailing byte and a removed body are `invalid/bad-content-coding`; `br`, `zstd`, `compress`, `aes128gcm` and malformed `Content-Encoding` values are `unverified/digest-coding-unsupported`; a zlib preset dictionary is `invalid/bad-content-coding` (RFC 1950 2.3); Repr-Digest over a `br` body still verifies. A 2 MiB gzip bomb is `unverified/body-too-large` under each limit alone and verifies with both raised, so the limit is what decided; the SHA-256 cap applies after decoding. A covered Content-Digest that fails stops the request before any decoding, and two signatures over Unencoded-Digest decode once.
  - Component identity (RFC 9421 2 and 2.1.2): reordered parameters and a `;sf` beside `;key` are repeats; HTAB is refused in derived components but allowed in field values.
  - RFC 9421 4 and the draft's 4.3, 5.2.2 and 5.5: an orphan label in either field is `invalid/orphan-label`; every signature is validated (a fourth one verifies) and every verified directory is listed; with no `Signature-Agent` a held key is `verified/url-less` with no agent, a key not held `unverified/agent-absent`; `https://agent.example:443` is ignored; 150 signatures in 38 KiB of headers each reach the crypto check.
  - Draft 5.5 agent types: `jwks_uri` and `cimd` members verify against their own identifiers, in every spelling (query, fragment, case, `:443`, dot segments, percent-encoding); unsupported or String-typed members are ignored; a key held for another URL never counts. IPv6 literal hosts verify under one RFC 5952 identifier.
  - The Appendix B fact for the verifying key: `valid`, `expired` once its `expires` passes, `invalid`, `none`; absent when URL-less.
  - Every algorithm (RFC 9421 3.3, less `hmac-sha256`), each with keys and signatures openssl makes over hand-written bases: Ed25519, P-256, P-384 and RSA 2048 and 3072 (PSS and v1.5) verify with `alg` declared, from the key where its type allows one algorithm, and with a matching JWK pin; a changed `@authority` fails each. RFC 9421 3.2 step 6: an RSA key with no pin and no `alg` is `alg-undetermined`; a pin decides when `alg` is absent; a pin to RSA-PSS refuses a v1.5 signature (`alg-mismatch`); a PSS signature presented as v1.5, and the reverse, is `bad-signature`; an `alg` for another key type is `alg-mismatch`; `hmac-sha256`, `ED25519`, `EdDSA`, `RS256` and other names are `unsupported-alg`. 12 wrong signature lengths are `bad-signature` and never reach the crypto; so are DER-encoded ECDSA signatures and RSA-PSS with a 0, 32 or 63-byte salt. A 2047-bit RSA key never verifies: keys.lua refuses the store that holds it. URL-less: the algorithm must be the same under every directory that lists the key. The draft's E.1.1 and E.1.2 verify; under the default policy their RFC 9421 B.1.2 key is a test key.
  - Every non-verified result in the suite is checked: none carries an identity or a proof.
- **`test_crypto`** (image test stage; SKIP where lua-openssl does not load): `crypto.lua` over the shipped lua-openssl. 34 openssl signatures over the five algorithms, RSA at 2048, 3072 and 4096 bits, verify; a changed message or signature does not; 8 per ECDSA curve, so r or s with its top bit set and without are both exercised. RFC 9421 B.2.1 to B.2.4 and B.2.6, the draft's E.1.1 and E.1.2. RSA-PSS: salts of 0, 32, 63 and 65 bytes, MGF1 with SHA-256 and SHA-256 itself are refused; PSS and v1.5 never confused. ECDSA: DER and one byte more or less raise; r = 0, s = 0 and swapped halves fail. A key with an algorithm for another type, `hmac-sha256`, an off-curve point and a P-384 point typed as P-256 raise. After every failure the OpenSSL error queue is empty.
- **`test_entry`:** `modsecurity_entry.lua` against a mock of `m` with libmodsecurity v3 semantics.
  - `m.getvar` raises on any name libmodsecurity cannot resolve (a `collection.key` outside `TX`, an unknown bare name), as the real engine's uncaught C++ exception would (`variable.h`, `stringMatchResolve`). An unset or empty variable returns no value at all, as the engine does.
  - Only 18 fixed names ever reach `m.getvar`, and the test lists them: four request variables (`REQUEST_METHOD`, `REQUEST_URI_RAW`, `REQUEST_BODY`, `INBOUND_DATA_ERROR`), three plugin variables (`TX.wba_stage`, `TX.wba_time`, `TX.wba_reason`) and eleven settings (`TX.wba_max_window`, `TX.wba_require_components`, `TX.wba_grant_agents`, `TX.wba_replay_dir`, `TX.wba_require_nonce`, `TX.wba_strict_field_lines`, `TX.wba_site_names`, `TX.wba_max_age`, `TX.wba_expiry_grace`, `TX.wba_malformed`, `TX.wba_grant_require_components`). Nothing derived from a request reaches it.
  - Both runs of a body-bound request: phase 1 never reads the body and records its time; phase 2 reads `REQUEST_BODY` once, honours `INBOUND_DATA_ERROR`, and judges freshness at phase 1's time. Unencoded-Digest over a binary gzip `REQUEST_BODY` (NUL bytes included) verifies in phase 2; a truncated body is `invalid/bad-content-coding`, a cut one `unverified/body-incomplete` without decoding, and a `br` body is decided in phase 1.
  - URL-less sets only `tx.wba_keyid`; a verified request sets `tx.wba_agents`, and `tx.wba_agent_proof` beside `tx.wba_agent`. A `jwks_uri` agent verifies through the entry; grants match an origin or an identifier in normal form exactly, never one for the other, and a grant not in normal form is `unverified/bad-config`. The operator's own `tx.wba_grant_require_components` list replaces the default `@method @path`. Raw-path aliasing, Host normalization (an empty port is no port) and header combining.

### Replay accounting: why not ModSecurity's collections

`lua/tests/live/collections-probe.sh` (not in `run_all.sh`) shows why `replay.lua` counts in files. In the CRS nginx image, `initcol:resource` with `setvar:resource.n=+1` keeps no count at all: libmodsecurity opens its LMDB database relative to nginx's working directory, `/`, which the nginx user cannot write. With a writable working directory, concurrent increments are lost, because `setvar` reads and writes in separate transactions. `replay.lua`'s `O_APPEND` append, its offset read back, gives 200 concurrent requests 200 different counts. The design is in [DESIGN.md](DESIGN.md#sessions-and-replay).

## Budgets the tests enforce

The tests validate outcomes, not timing. A few checks hold a ceiling, set several times above the measured cost, so that a quadratic path cannot return unnoticed; a slow machine passes them, a wrong algorithm does not. In `test_verify`: two 32 KB headers of inner spaces must trim in under 0.5 s (a linear scan; a backtracking pattern takes seconds); hundreds of `;sf`, `;key` and `@query-param` components over 8 to 16 KiB fields, 150 signatures in 38 KiB of headers each reaching the crypto check, and an 8 KiB `jwks_uri` value of dot segments or percent-encodings each stay under 250 ms, because each field, parsed field and query is worked out once per request and repeats are refused before any value is derived. In `test_coding`: the 10 MiB gzip bomb, a stacked one, floods of empty stored, fixed and dynamic blocks, 128 KiB of 15-bit literal codes and a 1 MiB gzip header under FHCRC each stop at the default decoding budget in under 0.5 s.

### Cost of a hostile request

ModSecurity runs the Lua for every request that carries a signature header, before any key is checked, so the verifier's worst case is a cost an unauthenticated client can impose; the budgets above bound it. Keyids are public (thumbprints of published keys), so any client can make the verifier run one verification per signature. There is no default cap on signatures per request, because the draft says a verifier must validate each one; `CONFIG.policy.max_signatures` in `modsecurity_entry.lua` sets one (`unverified/too-many-signatures`).

The body check runs only after a good signature from a held key. `max_sha256_body` defaults to 128 KiB because SHA-256 runs in Lua (`sha256.lua`, about 4 MB/s in the image), while SHA-512 runs in lua-openssl and is bounded only by `SecRequestBodyLimit`. The decoding budget (`max_decoded_body`, `max_decode_ratio` and the per-block charges) comes from `lua lua/tests/coding/bench.lua`, which builds each decoder path with `coding/bits.lua` and times it (best of three; a measurement, not a test):

| Path | Lua 5.3, CRS image (arm64, Finch) |
|---|---|
| Literals on fixed 8-bit codes | 7.0 MB/s |
| Literals on 15-bit codes (two table lookups each, the slowest bytes there are) | 3.6 MB/s |
| Matches of 258 at distance 1 (a bomb) | 22.4 MB/s |
| Stored blocks | 55.2 MB/s |
| The gzip CLI's `-6` output for 1 MiB of JSON-like text (ratio 5.5), CRC included: typical data | 9.5 MB/s |
| CRC-32 (gzip) / Adler-32 (zlib) | 31.1 / 45.8 MB/s |
| SHA-256 (`sha256.lua`), for scale | 4.2 MB/s |
| An empty fixed / stored block | 0.32 / 0.78 µs (1 / 3 slowest bytes) |
| An empty dynamic block (316 code lengths) | 191 µs (689 slowest bytes) |
| A dynamic block with the largest tables a code can force (32 subtables) | 247 µs (892 slowest bytes) |

So the worst a sender can make a decoded byte cost in the image is 3.6 MB/s plus the CRC: the default budget of 128 KiB is about 40 ms there, the same order as the SHA-256 cap's 31 ms. The block charges come from the same table: an empty stored or fixed block costs at most 3 bytes' worth and is charged 16; a dynamic block at most 892 and is charged 1024. Without them, a body of empty blocks would cost seconds of CPU at the image's 12.5 MiB `SecRequestBodyLimit` while producing nothing. Every symbol takes at most two table lookups (zlib's root and subtable scheme, 9-bit root), so no choice of code lengths is slower than the 15-bit row.

## Crypto: Wycheproof

`lua/tests/wycheproof/*.tsv` hold [C2SP/wycheproof](https://github.com/C2SP/wycheproof) `testvectors_v1` vectors (Apache-2.0), one file per algorithm, with the upstream commit and each source file's SHA-256 in the header; `convert.ts` regenerates them, and `run.lua` runs every file against `crypto.lua`. Public keys are in the key store's encoding, so the runner builds the same entries keys.lua does.

| File | Sources | Vectors | Valid / invalid / acceptable |
|---|---|---|---|
| `ed25519.tsv` | `ed25519_test.json` | 151 | 88 / 63 / 0 |
| `ecdsa-p256-sha256.tsv` | `ecdsa_secp256r1_sha256_p1363_test.json` (r ‖ s) | 262 | 173 / 89 / 0 |
| `ecdsa-p384-sha384.tsv` | `ecdsa_secp384r1_sha384_p1363_test.json` (r ‖ s) | 280 | 193 / 87 / 0 |
| `rsa-pss-sha512.tsv` | `rsa_pss_4096_sha512_mgf1_64_test.json`, `rsa_pss_misc_test.json` | 329 | 133 / 196 / 0 |
| `rsa-v1_5-sha256.tsv` | `rsa_signature_{2048,3072,4096}_sha256_test.json` | 776 | 24 / 749 / 3 |

`rsa_pss_misc` holds one valid signature for each combination of hash, MGF1 hash and salt length. RFC 9421 3.3.1 fixes SHA-512, MGF1 with SHA-512 and a 64-byte salt, so the converter marks the 149 made with other parameters invalid: they test that a wrong salt length or MGF1 hash is refused, never auto-detected. "Acceptable" vectors (Wycheproof's own term: either outcome is allowed) are counted, not judged.

The `Dockerfile`'s `test` stage runs all 1798 against the exact lua-openssl build it ships (0.11.1, pinned by commit, over the image's OpenSSL): 0 disagreements.

## Why lua-openssl

All official CRS images link plain Lua 5.3, not LuaJIT, so FFI-based libraries such as `lua-resty-openssl` are out, and plain Lua cannot do RSA or ECDSA at a useful speed. lua-openssl (MIT, maintained) is a C binding to OpenSSL's EVP interface that builds against the image's OpenSSL 3, so its patching follows the distribution's OpenSSL. Debian's `lua-luaossl` verifies through OpenSSL's legacy `EVP_VerifyFinal`, which cannot do Ed25519 ([wahern/luaossl#188](https://github.com/wahern/luaossl/issues/188), open). The other bindings (luamonocypher, `luazen`, the `lua-sodium` forks) have no ECDSA or RSA. The trade-off is in [DESIGN.md](DESIGN.md#crypto-dependency).
