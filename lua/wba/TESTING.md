# Testing

Every layer checks against something other than this code's own output. One command runs them all:

```bash
lua/tests/run_all.sh            # Lua suites, corpora, vectors, mutants, fixture freshness, key-sync
lua/tests/run_all.sh --live     # plus the image test stage, live suite, Quick start, registry path, real-IP checks, bot lists, the Debian guide and the go-ftw tests (Finch)
DOCKER=docker lua/tests/run_all.sh --live   # the same on Docker
DOCKER="sudo finch" lua/tests/run_all.sh --live   # on Linux, where Finch runs as root
lua/tests/interop/interop.sh    # against the LATEST npm web-bot-auth and Stytch's recipe (not hermetic; Finch, or DOCKER=docker)
```

## Continuous integration

> This preview does not include the workflows. They run in the development repository; run the suites yourself with `lua/tests/run_all.sh`. The section is kept as a record.

Five workflows run on GitHub's hosted Ubuntu 24.04 runners. The container scripts take their CLI from `DOCKER` (Finch by default), and CI proves both Finch and Docker. Finch is its Ubuntu package, pinned by version and SHA-256 in `.github/scripts/install-finch.sh`, installed after the runner's Docker is removed (its `containerd.io` conflicts with the containerd Finch depends on); Docker is the runner's own.

| Workflow | When | What |
|---|---|---|
| `wba.yml` | every push and pull request, except a change only to files no job reads; weekly; by hand | one job runs `run_all.sh` on Lua 5.3 (the CRS images' version) with Bun and Node, the mutants in two shards at once (`JOBS=2`, one per vCPU), then `run_all.sh --suites-only` on 5.4: mutants and key-sync do not depend on the Lua version, so they run once. The image test stage, every live check, the Quick start and the real-IP checks, once on Finch and once on Docker |
| `crs-matrix.yml` | when `crs-images.txt` or the Dockerfile changes on master; the 1st of each month; by hand | `matrix.sh` on every image in `crs-images.txt`, one job per image: on Finch, and on Finch and Docker when run by hand (no inputs; Checkov CKV_GHA_7). A job fails unless its row reads PASS (`matrix.sh` itself exits 0 whatever the verdicts); the run summary has one table, and the rows are kept 35 days |

Dependabot (`.github/dependabot.yml`) proposes updates to the SHA-pinned actions each week, taking no release younger than seven days. The CRS base image (an `ARG` in the Dockerfile, which Dependabot does not read), Finch, ASH and Bun (`bun-version` in the workflows) are bumped by hand.

Each change is tested once. A gate job (`.github/scripts/already-verified.sh`) skips a run that would repeat one: a pull request from a branch of this repository, whose push run already tests the same commit, and a master commit whose git tree already passed the same workflow in a push run on a branch: a fast-forward, or a merge-button commit of an up-to-date branch (tree hashes are content-addressed, so the same tree is the same files, workflows included; pull request runs never count, since a fork controls their workflow file). It skips only a whole run, never part of one, and it fails open: a re-run, the schedule, a run by hand or any error in the check runs every job. `lint-workflows.yml` skips a pull request from a branch here at job level instead. `wba.yml` also ignores pushes that change only files none of its jobs reads: `research/`, `preview/`, the two top-level READMEs, `CONFORMANCE.md`, `DESIGN.md`, this file, `.ash/`, Dependabot's configuration and the other workflows. `lua/wba/README.md` is not on that list, because `run_all.sh` checks its recipes against `recipes.conf`. A file goes on the list only when nothing reads it. Once the repository is public with required checks, these path filters must become job-level skips: a workflow that never starts leaves its required check pending. The weekly run tests master in full whatever changed.

Cost, in billed minutes (GitHub rounds every job up to a whole minute): before the gate (2026-10-09), about 40 per change; with it, about 20; since 2026-10-10 about 13 (one Lua job of about 3 minutes instead of two of 3 to 4, no lint job unless its files change), plus two one-minute gate jobs on master. Every job has a timeout a few times its usual length (gate 3, Lua 10, live 12, ASH 8, matrix image 15, others 5; interop 20, by hand), so a hung run cannot spend the month's minutes, and every `curl` CI runs has a `--max-time`.

Every workflow follows GitHub's hardening guide (https://docs.github.com/en/actions/reference/security/secure-use): third-party actions pinned to full-length commit SHAs, a read-only token (`contents: read`), and matrix values passed to scripts through intermediate environment variables. As in CRS, no checkout keeps the token (`persist-credentials: false`); every job also has a timeout. Two of the guide's suggestions are not taken yet: CODEOWNERS (there is one maintainer) and an OpenSSF Scorecard. A newer push cancels an older run on the same branch, but a master run always finishes. One recommended control is missing: required status checks on master. A private repository on GitHub Free cannot protect a branch (the API answers "Upgrade to GitHub Pro or make this repository public"), so nothing on GitHub stops a red commit reaching master; merge only after every workflow on the branch has passed.

## Conformance suites

- **`test_sf_corpus`:** every record of httpwg/structured-field-tests (`sf-corpus/`, commit `00462dd`). Parse records must parse to `expected` (or fail when `must_fail`), and `expected` must serialize to `canonical`; serialization records must serialize or fail as marked. The corpus tells Integers from Decimals by JSON literal (`1` vs `1.0`), which JavaScript's `JSON.parse` erases, so the files are read by a small test-only Lua JSON reader. Shown able to fail: the previous parser fails over 700 of them.
- **`test_components`:** each component example in RFC 9421 2.1 and 2.2 as a signature-base line, byte for byte; the URL Standard's decoding rules (`+`, stray `%`, U+FFFD replacement by maximal subpart); and 2720 `@query-param` vectors from `query-param/gen.ts`, whose oracle is the runtime's own `URLSearchParams`. `@query-param` with any parameter besides `name`, before or after it, is `unsupported-component` (2.2.8 defines only `name`).
- **`test_negative_vectors`:** each vector's request, body, clock and key, with the test key allowed and the window cap off (the draft's E.2 parameters, as in `test_verify`), run as phase 2 sees it (body available), so the outcome is the final one. A vector must reach its outcome *for its intended reason*: with the window cap left on, all of them would be `invalid` for the wrong reason, and the suite says so. 16 match as written, and NV-10 is dispositioned (it expects RFC 9651 4.2's "malformed" branch, which `tx.wba_malformed=reject` gives and the suite checks; the default ignores the field). NV-08 (a Content-Digest that does not match the body) needed a disposition until the RFC 9530 check existed.

## Lua unit suites

Needs `lua` 5.3+ and `openssl` 3.x. openssl is the independent oracle for every algorithm (`helpers.lua`): it signs, it verifies, and it makes every encoding the oracle needs (RSA and EC SubjectPublicKeyInfo, ECDSA r ‖ s to and from DER) with `asn1parse`, so the verifier is never checked against a signature or encoding this code produced.

- **`test_base64`:** RFC 4648 vectors, every byte value round-tripped, and RFC 9651 4.2.7's tolerance of missing or partial padding and non-zero pad bits.
- **`test_structured_fields`:** typed parsing, and byte-exact re-serialization of the draft's E.2.1 `Signature-Input`, including `;key=` and a quoted `nonce`. It also covers 23 malformed inputs that must raise: control bytes, hex and exponent "integers", decimals, duplicates. Display Strings reach each UTF-8 guard the corpus does not (its invalid cases all fail at the first continuation byte): an overlong E0 form (`%"%e0%80%af"`), F4 above U+10FFFF (`%"%f4%90%80%80"`) and a third byte that is not a continuation byte (`%"%e2%82%28"`) are refused; U+40000 (`%"%f1%80%80%80"`) and U+10FFFF (`%"%f4%8f%bf%bf"`) parse and re-serialize.
- **`test_sigbase`:** the RFC 9421 B.2.6 base and both draft E.2 bases rebuilt byte for byte, with each published signature verifying over the rebuilt base. RFC 9421 B.2.1 to B.2.3 (`rsa-pss-sha512`, test-key-rsa-pss), B.2.4 (`ecdsa-p256-sha256`, test-key-ecc-p256) and the draft's E.1.1 and E.1.2 (`rsa-pss-sha512`) verify over the bases built here; those signatures are randomized, so only a byte-exact base passes. The vectors are in `rfc_vectors.lua`, copied from the documents with RFC 8792 wrapping undone.
- **`test_sha256`:** the FIPS 180-4 example vectors (empty, `abc`, the 448- and 896-bit messages, one million `a`), RFC 9421 7.2.8's digest, and openssl for every message length from 0 to 1000 bytes, which crosses every padding boundary. In the image test stage, `crypto.lua`'s SHA-512 (lua-openssl) gets the same comparison.
- **`test_coding`:** `coding.lua`, the content codings.
  - Every line of `coding/vectors.tsv` (2895), each decoded and compared with what zlib did with it: the same refusal, or the same bytes (length and SHA-256). The file holds zlib's own output for eight inputs over levels 0, 1, 6 and 9, four strategies, window sizes 9 and 12 and memLevel 1 (raw, zlib and gzip); three streams flushed after each of 40 writes; 46 hand-built streams for each RFC 1951 error and each edge zlib accepts (distance 32768, a repeat crossing into the distance lengths, a single one-bit code, length 258 spelt 284+31); zlib and gzip header and trailer errors, wrong wrappers and both RFC figures; every truncation and every single-bit flip of five small streams; and 700 random inputs.
  - The RFCs' figures by their published digests; RFC 1952 members and RFC 1950 single streams, where zlib-based tools differ from the text (trailing bytes are refused); stacked codings; FDICT, which RFC 1950 2.3 forbids where no dictionary is defined, as corrupt; unknown codings; LEN 65535 and a match 32768 back into stored bytes.
  - The budget to the unit, for a fixed and a dynamic block. A 10 MiB gzip bomb and the same gzipped again (gzip CLI), 8193 empty fixed and stored blocks, 129 empty dynamic blocks, 140000 literals on 15-bit codes, and a 1 MiB FCOMMENT under FHCRC each stop at the default budget, each in under 0.5 s. The floods, the 15-bit literals and the header also decode with no budget, so the budget is what stopped them (the bombs' counterpart is in `test_verify`, where a 2 MiB bomb verifies with the limits raised).
  - Every prefix of a gzip stream with a dynamic block (the gzip CLI's `-9` over 4000 random letters, about 2.3 KB) is `corrupt`, and none raises.
- **`test_keys`:** the key-store contract (format version 2).
  - `fixtures/wba-keys.tsv` is the exact file `wba-keysync` emits; its test asserts the same bytes. It holds Ed25519, P-256, P-384 and RSA keys, with and without an `alg` pin, every proof state (`valid`, `invalid`, `none`) and a `jwks_uri` identifier on an IPv6 literal. The EC and RSA keys were generated by openssl for it (private halves discarded), and openssl recomputes each keyid as its RFC 7638 thumbprint.
  - Every row of `fixtures/identifiers.tsv`: a request's directory member (strict), an operator's origin, and `jwks_uri` / `cimd` URLs; every identifier returned is its own normal form.
  - Every malformed store rejected whole, 36 cases: key types, `alg` names for another type, `hmac-sha256` and JOSE names, compressed or wrong-curve points, RSA `n` and `e` that are not minimal, even, too short, too long or too large; a proof that is not `valid`/`invalid`/`none`, a `valid` without its expiry, an expiry on another state; identifiers with a query or an IPv6 literal not in RFC 5952 form.
  - RSA bounds against keys openssl makes: 2047 and 1024 bits refused, 2048 accepted; and the edges, 16384 bits, e = 3, a 256-bit e.
  - A version 1 store still loads: every key Ed25519, no `alg`, proof `none`.
- **`test_verify`:** the state machine.
  - Both draft vectors verify.
  - Freshness, `alg`, `keyid` checks.
  - Coverage rules; attribution cannot be moved to another agent.
  - Signature-Agent URL and type rules; component rules.
  - Several signatures on one request, including the draft's Appendix D.2 shape: an outer signer that also covers the inner signer's member is attributed to its own member, never the inner one.
  - Key-store and crypto failure modes.
  - Header trimming is timed: two headers of 32,000 inner spaces must finish in under 0.5 s (the old backtracking trim took 7.1 s on the same Mac).
  - Lowercasing touches only A-Z, including under a Latin-1 locale where `string.lower` maps byte 0xC0 to 0xE0.
  - Body digests (RFC 9530), with the RFCs' own example digests: phase 1 pends, a matching body verifies, an added or removed byte is `invalid/digest-mismatch`; the strongest covered algorithm decides (RFC 9530 2's two-member example verifies on its SHA-512); an appended, uncovered member cannot vouch for a swapped body; Deprecated and unknown algorithms are ignored; malformed fields are `invalid` without the body; incomplete and oversized bodies are `unverified`; a pending signature outranks an invalid one; the body is read only after a good signature, and each algorithm runs once per request.
  - Partial content (RFC 9530 3, RFC 9110 14.4 and 14.5): `Content-Range` on POST and PATCH is ignored and the digest verifies; a PUT verifies only when its range is the whole representation (in any letter case) and the content has that length; nine other ranges, an Unencoded-Digest on a partial PUT, and a range claiming 40 bytes over 18 are `unverified/digest-partial`; Content-Digest is checked on a partial PUT.
  - Unencoded-Digest over coded bodies (draft-ietf-httpbis-unencoded-digest-05): the draft's Figure 2 gzip request verifies with its sha-256 and sha-512 Unencoded-Digest and, together, its Repr-Digest over the coded bytes; unknown member parameters are ignored (draft 3); `x-gzip`, letter case, `identity`, empty list elements, `deflate` (a zlib-made stream) and `deflate, gzip` stacked all verify; the wrong order, a body that is not its coding, a truncated stream, a trailing byte and a removed body are `invalid/bad-content-coding`; ten `br`, `zstd`, `compress`, `aes128gcm` and malformed `Content-Encoding` values are `unverified/digest-coding-unsupported`, and a zlib preset dictionary is `invalid/bad-content-coding` (RFC 1950 2.3); Repr-Digest over a `br` body still verifies. A 2 MiB gzip bomb is `unverified/body-too-large` under each limit alone and verifies with both raised, so the limit is what decided; a stacked bomb too; the SHA-256 cap applies after decoding. A covered Content-Digest that fails stops the request before any decoding, and two signatures over Unencoded-Digest decode once. `Want-*` fields change nothing.
  - Component identity (RFC 9421 2 and 2.1.2): reordered parameters and a `;sf` beside `;key` are repeats; HTAB is refused in derived components but allowed in field values.
  - RFC 9421 4 and the draft's 4.3, 5.2.2 and 5.5: an orphan label in either field is `invalid/orphan-label`; every signature is validated (a fourth one verifies) and every verified directory is listed; with no `Signature-Agent` a held key is `verified/url-less` with no agent, a key not held `unverified/agent-absent`; `https://agent.example:443` is ignored; 150 signatures in 38 KiB of headers, each reaching the crypto check, stay under the 250 ms budget (13 ms).
  - Draft 5.5 agent types: `jwks_uri` and `cimd` members verify against their own identifiers, in every spelling (query, fragment, case, `:443`, dot segments, percent-encoding); unsupported or String-typed members are ignored; a key held for another URL never counts. Normalizing a client's 8 KiB `jwks_uri` value of dot segments or percent-encodings stays under the 250 ms budget.
  - IPv6 literal hosts verify under one RFC 5952 identifier; uppercase hex, `:443` and zone identifiers in an origin are ignored.
  - The Appendix B fact for the verifying key: `valid`, `expired` once its `expires` passes, `invalid`, `none`; absent when URL-less.
  - Every algorithm (RFC 9421 3.3, less `hmac-sha256`), each with keys openssl makes and signatures openssl makes over hand-written bases:
    - Ed25519, P-256, P-384 and RSA 2048 and 3072 (PSS and v1.5) verify with `alg` declared, from the key where its type allows one algorithm, and with a matching JWK pin; a changed `@authority` fails each.
    - RFC 9421 3.2 step 6: an RSA key with no pin and no `alg` is `alg-undetermined`; a pin decides when `alg` is absent; a pin to RSA-PSS refuses a v1.5 signature (`alg-mismatch`, 7.3.6); a PSS signature presented as v1.5, and the reverse, is `bad-signature`; an `alg` for another key type is `alg-mismatch`; `hmac-sha256`, `ED25519`, `EdDSA`, `RS256` and other names are `unsupported-alg`.
    - Lengths: 12 wrong lengths (ECDSA ±1 byte and the other curve's, Ed25519 ±1, RSA k ± 1 and another key's k) are `bad-signature` and never reach the crypto; so are DER-encoded ECDSA signatures, while the same key's r ‖ s verifies.
    - RSA-PSS signed with a 0, 32 or 63-byte salt is `bad-signature`.
    - A 2047-bit RSA key never verifies: keys.lua refuses the store that holds it. RSA, P-256 and P-384 keys verify through keys.lua's parsed store.
    - URL-less: the algorithm must be the same under every directory that lists the key (one pin, an open entry, two different pins).
    - The draft's E.1.1 and E.1.2 verify; under the default policy their RFC 9421 B.1.2 key is a test key.
  - Every non-verified result in the suite is checked: none carries an identity or a proof.
- **`test_crypto`** (image test stage; SKIP where lua-openssl does not load): `crypto.lua` over the shipped lua-openssl.
  - 34 openssl signatures over the five algorithms, RSA at 2048, 3072 and 4096 bits, verify; a changed message or signature does not; 8 per ECDSA curve, so r or s with its top bit set (a 00 byte in DER) and without are both exercised.
  - RFC 9421 B.2.1 to B.2.4 and B.2.6, the draft's E.1.1 and E.1.2.
  - RSA-PSS: salts of 0, 32, 63 and 65 bytes, MGF1 with SHA-256 and SHA-256 itself are refused; PSS and v1.5 never confused.
  - ECDSA: DER and one byte more or less raise; r = 0, s = 0 and swapped halves fail.
  - A key with an algorithm for another type, `hmac-sha256`, an off-curve point and a P-384 point typed as P-256 raise.
  - After every failure the OpenSSL error queue is empty.
- **`test_entry`:** `modsecurity_entry.lua` against a mock of `m` with libmodsecurity v3 semantics.
  - `m.getvar` raises on any name libmodsecurity cannot resolve (a `collection.key` outside `TX`, an unknown bare name), as the real engine's uncaught C++ exception would (`variable.h`, `stringMatchResolve`).
  - The test asserts that only six constant names ever reach `m.getvar`: `REQUEST_METHOD`, `REQUEST_URI_RAW`, `REQUEST_BODY`, `INBOUND_DATA_ERROR`, `TX.wba_stage`, `TX.wba_time`.
  - Both runs of a body-bound request: phase 1 never reads the body and records its time; phase 2 reads `REQUEST_BODY` once, honours `INBOUND_DATA_ERROR`, and judges freshness at phase 1's time.
  - Unencoded-Digest over a binary gzip `REQUEST_BODY` (NUL bytes included, as `lua_pushlstring` delivers it) verifies in phase 2; a truncated body is `invalid/bad-content-coding`, a cut one `unverified/body-incomplete` without decoding, and a `br` body is decided in phase 1.
  - URL-less sets only `tx.wba_keyid`; a verified request sets `tx.wba_agents`, and `tx.wba_agent_proof` beside `tx.wba_agent`.
  - A `jwks_uri` agent verifies through the entry; grants match an origin or an identifier in normal form exactly, never one for the other, and a grant not in normal form is `unverified/bad-config`.
  - The operator's own `tx.wba_grant_require_components` list replaces the default `@method @path`: with `@method @path @query`, a signature covering `@method @path` verifies but is not granted, and one covering all three is granted; the default list grants the first.

  - In the image test stage it also runs the entry with `crypto.lua` over lua-openssl itself (not the oracle): ECDSA, RSA-PSS and Ed25519 signatures, a changed `@authority`, and a SHA-512 Content-Digest decided in phase 2.

- **`test_log`:** `wba_log.lua` (the JSON line) against a mock of `m`: every field typed, unverified fields `null`, no line for unsigned requests, client text escaped so a line is always one valid JSON object. The longest line a request can make (every field filled to its cap with 1-byte characters, 15-digit integers) is 4010 bytes, within one 4096-byte pipe write. ## Replay accounting: why not ModSecurity's collections

`lua/tests/live/collections-probe.sh` reproduces what decided the design. It runs a CRS nginx image three times, 200 concurrent requests each, counting them in a rule or a Lua script:

| Run | Count kept by | Result |
|---|---|---|
| 1 | `initcol:resource` + `setvar:resource.n=+1` (LMDB), image as shipped | no count at all: libmodsecurity opens `./modsec-shared-collections` relative to nginx's working directory, `/`, which uid 101 cannot write |
| 2 | the same, with `-w /tmp` | the database opens, and concurrent increments are lost: `setvar` reads and writes in separate transactions |
| 3 | a Lua `O_APPEND` append, offset read back (replay.lua's method) | 200 different counts, none lost |

Measured on `4.29.0-nginx-202609241109` (ModSecurity 3.0.17), by hand and then with the script (2026-10-03): run 1 logged no count at all; run 2 left the counter at 70 (by hand) and 62 (script: 61 distinct values among 200 logged) after 201 increments; run 3 gave 200 distinct counts both times. Also found: a `setvar` in the same rule as its `initcol` runs before the collection exists.

## Live

`lua/tests/live/run.sh` builds the Dockerfile and generates keys. It runs the container with the key directory mounted, plus a test-only rule (`wba-test-after.conf`) that logs each request's `tx.wba_*`. Then it asserts: Every signed case goes over the image's TLS port (HTTP/1.1 unless the case is HTTP/2), because the guard refuses signed cleartext; outcomes are logged in phase 5, so a request the rules answer with 400 still reports its `tx.wba_*`.

- **13 request outcomes:** verified; raw `%3F` path verified; decoded-path alias invalid; tampered Host; unknown key; dotted component name; expired; `Host: example.com:443`; 8 `Signature` headers; unsigned; malformed; unsigned absolute-form (`not-signed`, still accepted); a signed request whose User-Agent claims Googlebot (`verified`: WBA vouches for the signer, not the UA).
- **Signed requests with a non-origin-form target:** seven request lines, each must get HTTP 400 *and* leave no `tx.wba_*` log line, which shows the guard answered before ModSecurity ran.
  - `@query` smuggling: `GET http://example.com?evil=1` carrying a signature over `"@query": ?`.
  - Host mismatch: `GET http://other.example/` with `Host: example.com`.
  - The same mismatch as `GET  http://...` (two spaces), `M-SEARCH http://...` and `X_FOO http://...`. nginx accepts all three; the first guard's regex matched none of them, and each came back `verified` (reproduced 2026-09-30).
  - Two *correctly* signed absolute-form requests, also refused. That is the cost of the guard, and the project's deviation from RFC 9112 3.2.2, one of its two declared deviations (CONFORMANCE.md, Summary by standard).
  - Each spelling above, sent unsigned, reaches ModSecurity (`not-signed/no-signature`): nginx's own parser accepts every one, so each 400 above is the guard's.
  - Without any guard, the plain host-mismatch request also came back `verified`. The `@query` case is refused inside the Lua as well, as `invalid/missing-component`.
- **The compliant alternative, tested and refuted (2026-10-01):** rewriting `Host` to the request-line authority with headers-more, so absolute-form could be accepted. With connector v1.0.4, rewriting `Host` to `probe.example` on every request still left ModSecurity logging `REQUEST_HEADERS:Host = "example.com"`, with headers-more loaded after ModSecurity and before it. v1.0.4 registers its header processing in nginx's rewrite phase (`ngx_http_modsecurity_module.c`, tag v1.0.4); `master` registers in the access phase.
- **HTTP/2, on the TLS port** (required: the run fails if a case went over HTTP/1.1):
  - signed requests over curl `--http2` verify, and a tampered authority is `invalid/foreign-authority`;
  - a request carrying only `:authority` verifies, so nginx hands it to ModSecurity as the Host header;
  - `:authority` and `host` that disagree, either way round, get 400 from nginx and leave no `tx.wba_*` log line (`h2.ts` sends them; curl cannot).
- **0 `worker process ... exited on signal` lines.**
- **The RFC rules, live:** a signed request over cleartext gets 400 from nginx and leaves no `tx.wba_*` line; unsigned cleartext is `not-signed`; no `Signature-Agent` with the key held is `verified/url-less` with `agent=` empty and the keyid set; a Signature-Input label with no Signature member is `invalid/orphan-label`; an unparsable Signature-Input is `not-signed/unparsable-field` by default, and with `tx.wba_malformed=reject` it is `invalid/malformed-headers` and gets 400.
- **Lua run counts from the debug log:** a request with 8 `Signature` headers is verified in 1 run (plus 1 run that writes its log line); an unsigned request causes 0.
- **Key rotation:** the store is rewritten with `wba-keysync`'s own atomic writer and picked up without a restart. The old key becomes `unverified/unknown-key` and the new key verifies.
- **Crypto module missing:** with the crypto module hidden, a valid signature gives `unverified/engine-error` (last run with `luamonocypher.so`; `run.sh` now hides lua-openssl's `openssl.so`, whose load failure stops `modsecurity_entry.lua` the same way).
- **Logs (rule 7, `wba_log.lua`):** each case's transaction is found by the `unique_id` in its audit-log entry, and its JSON line by the same `unique_id`.
  - A verified request's line has `status`, empty `reason`, the directory URL, a 43-character `keyid`, `label`, integer `created` and `expires`, `granted:false`, a 64-hex `sighash` and `covered`. A URL-less one has `agent:null` and `reason:"url-less"`. A tampered one has `invalid/bad-signature` and every signature field `null`. An unsigned one has no line.
  - No line holds a base64 run of 80 characters or more, so no signature. The audit log's part B does hold raw signatures, which the README warns about.
  - Found while building this: a rule's `log` action writes nothing in this image (ModSecurity-nginx logs rule messages at nginx `info`; the image runs nginx at `warn`), which is why the log is a script.
- **`recipes.conf` as shipped:**
  - A: unsigned requests to `/agents/x`, `/./agents/x`, `//agents/x`, `/AGENTS/x`, `/%61gents/x`, `/agents` and `/agents;jsessionid=x/secret` get 403 from rule 9534130; `/x/../agents/x` gets 403 from CRS's path-traversal rules first; `/agentsx` is another path, and rule 9534130 does not match it.
  - C: a granted bot gets `tx.bot_management_exempt=1` (test rule 9534917 logs it), and a verified bot whose signature covers only `@authority` does not.
  - F: a published test key (`invalid/test-key`) and a body that is not the one signed (`invalid/digest-mismatch`) get 403 from rule 9534135, beside the forged and foreign signatures.
  - B: an unsigned request and a URL-less verified one, each claiming `ExampleBot/1.0`, get 403 from rule 9534131. Before rule 1 gave `tx.wba_agent` the default `n/a`, both would have passed.
  - A verified request to `/agents/x`, a verified `ExampleBot` and an unsigned request claiming nothing pass every rule (502 from the dead test backend).
- **Operator settings** (a second container, `wba-test-config.conf` over the shipped config): a granted origin logs `"granted":true`; `tx.wba_require_components=@method @path` makes a signature without them `unverified/insufficient-coverage` and one with them `verified`; `tx.wba_max_window=60` makes a 605 s window `invalid/window-too-long`; a malformed `tx.wba_max_window` gives `unverified/bad-config`, in the log line, with the debug log naming the setting.
- **Header order:** two `X-A` lines signed as `first, second` verify, and the same lines sent the other way round are `invalid/bad-signature`, so libmodsecurity's `REQUEST_HEADERS` keeps arrival order.
- **Body digests (RFC 9530), 20 checks.** Body cases log their phase-1 outcome, and their final outcome in phase 5, which runs whether or not phase 2 did:
  - every body-bound case is `unverified/digest-pending` at the end of phase 1;
  - a matching body verifies with SHA-256 and with SHA-512 (lua-openssl), over HTTP/1.1, `Transfer-Encoding: chunked` and HTTP/2;
  - a changed body and a removed body are `invalid/digest-mismatch`;
  - with `ctl:requestBodyAccess=Off`, phase 2 never runs and the request stays `unverified/digest-pending`;
  - a 1 MiB body verifies with SHA-512 and is `unverified/body-too-large` with SHA-256;
  - in a container started with a 64-byte `SecRequestBodyLimit` and `ProcessPartial`, a cut body is `unverified/body-incomplete`.
- **Content codings and partial PUT, 20 checks** (octet-stream bodies, so ModSecurity's body processors leave the coded bytes alone; the gzip CLI encodes, openssl hashes):
  - Unencoded-Digest over a gzip body verifies (SHA-256), and over `x-gzip` (SHA-512); a wrong digest is `invalid/digest-mismatch`; the same gzip without its 4-byte trailer is `invalid/bad-content-coding`;
  - 10 MiB of zeros gzipped (about 10 KB sent) is `unverified/body-too-large`: the decode budget, not the body limit, stops it;
  - a `br` body is `unverified/digest-coding-unsupported` at the end of phase 1 and stays so; Repr-Digest over gzip bytes verifies without decoding;
  - `Content-Range: bytes 0-4/100` on a POST is ignored and the request verifies; a PUT with `bytes 0-4/18` is `unverified/digest-partial` from phase 1; a PUT with `bytes 0-17/18`, the whole representation, verifies.
- **Every algorithm, 10 checks:** keys generated by openssl each run (P-256, P-384, three RSA 2048), signatures made by openssl. P-256 with and without the `alg` parameter, P-384, RSA-PSS and PKCS #1 v1.5 verify; an RSA key whose JWK has no `alg`, signed with none, is `invalid/alg-undetermined`, and verifies when the signer names one; `rsa-v1_5-sha256` against a JWK pinned to `rsa-pss-sha512` is `invalid/alg-mismatch`; a DER ECDSA signature is `invalid/bad-signature`; `hmac-sha256` is `invalid/unsupported-alg`.
- **Asking for a signature (draft 5.3), 6 checks:** recipe A's 403 for `/agents/x`, `/AGENTS/x` and `/agents;jsessionid=x/secret` each carries `Accept-Signature` matching `sig1=("@authority" "@method" "@path" "signature-agent";key="sig1");created;expires;nonce="<32 hex>";tag="web-bot-auth"` and `Cache-Control: no-store`; the two nonces differ; CRS's own 403 (`/x/../agents/x`) carries none; a request signed as asked, with the first nonce, verifies and passes recipe A (502 from the dead backend).
- **Replay accounting, 11 checks** (a container with `wba-test-replay-config.conf`): run.sh prints a signed request once and sends the same bytes again. The first use passes; the second gets 429 with `Accept-Signature`, from rule 9534133, and its log line says `"uses":2`; a third, also 429, runs the Lua twice (verify, log) and writes one log line, so the error page re-runs nothing; two ECDSA signatures over one base (gen.lua's `NOW` fixed, different bytes): the first passes, the second gets 429; 20 simultaneous sends of one signature give exactly one 502 and nineteen 429; a nonce reused under a different signature passes the first time and gets 429 from rule 9534134 the second; a replay directory the workers cannot write (the read-only key store) gives `unverified/replay-unavailable`.
- **Agent types and proofs, 6 checks:** a `type=jwks_uri` member with a query verifies and names the identifier without it; `type=cimd` verifies; the same URL untyped is `unverified/bad-agent-url` (a directory member is an origin); a key stored with a valid possession proof logs `"agent_proof":"valid"`.

## Cost of a hostile request

ModSecurity runs the Lua for every request that carries a signature header, before any key is checked, so its worst-case cost is a cost an unauthenticated client can impose. Two measurements, both timing the full `verify()` (Apple M1 Pro, Lua 5.5.1).

**One header at a time:** 13 adversarial shapes at 8 KiB and 32 KiB. A linear path shows a ratio near 4, a quadratic one near 16.

- **Shapes:** inner whitespace, long strings, escaped strings, long tokens, long binary, many dictionary members (unique and duplicate), many parameters, many inner-list items, many parameters per item, many covered headers, many header instances, a long `Signature-Agent` dictionary.
- **Worst ratio:** 4.3. **Worst cost:** 13 ms at 32 KiB.

**Components and field size together:** the one-header method above cannot see a cost that is the product of two sizes, and it missed one. The fourth review found that every covered component re-parsed its whole field, so hundreds of `;sf`, `;key` or `@query-param` components over one 8 KiB field cost seconds:

| Shape | Before | After |
|---|---|---|
| 2 x 575 `"priority";sf` over an 8 KiB Dictionary | 2,653 ms | 6 ms (repeats refused first, RFC 9421 2.5) |
| 800 distinct `;key` over an 8 KiB Dictionary | 1,264 ms | 7 ms |
| 400 distinct `@query-param` over a 6 KiB query | 745 ms | 5 ms |
| one `;bs` over 8,000 inner spaces | 228 ms | 1 ms |

Each field, parsed field and the query's parameters are now worked out once per request. `test_verify` 14f holds both dimensions under a 250 ms budget, and three mutants (memo off, the backtracking obs-fold regex, repeats derived before refused) fail it.

Earlier, before the third review's fix, 8,000 inner spaces in one header cost 218 ms through the old trim.

**The body check (RFC 9530).** Only a good signature from a key in the store reaches it, so this is the cost a holder of a valid signature can impose. Hashing, measured inside the image's test stage (Lua 5.3, arm64, Finch):

| Body | SHA-256 (`sha256.lua`) | SHA-512 (luamonocypher, until 2026-10-02) | SHA-512 (lua-openssl, `crypto.sha512`) |
|---|---|---|---|
| 1 KiB | 0.27 ms | 0.003 ms | |
| 64 KiB | 15.6 ms | 0.14 ms | |
| 1 MiB | 249 ms | 2.3 ms | 0.76 ms |

That is about 4.2 MB/s against 450 MB/s (now about 1.4 GB/s), which is why `max_sha256_body` defaults to 128 KiB (about 31 ms) while SHA-512 is bounded only by `SecRequestBodyLimit`. lua-openssl's SHA-256 takes 0.45 ms per MiB in the same image; moving SHA-256 to it would make the cap unnecessary, and is left for its own change (DESIGN.md, Crypto dependency). On Lua 5.5.1 (M1 Pro), the body, a digest field with thousands of members, the same in phase 1, and three signatures over one body all scale linearly from 16 KiB to 64 KiB (ratios 3.7 to 4.1); three signatures cost what one does, because each algorithm runs once per request. The header shapes above were re-measured after the change: worst ratio 4.4, and the components-times-field-size shapes stay under 8 ms.

**Verification by algorithm.** A signature reaches the crypto only if its keyid is held, but keyids are public (they are thumbprints of published keys), so any client can name one and make the verifier run a verification per signature. `crypto.verify` end to end (key rebuilt and parsed, then verified), in the image's test stage (Lua 5.3, OpenSSL 3.5.7, arm64, Finch): Ed25519 0.096 ms, P-256 0.080 ms, P-384 0.47 ms, RSA 2048 0.04 ms, 4096 0.10 ms, 8192 0.30 to 0.42 ms, 16384 1.1 ms (a synthetic modulus: a failing check costs the same exponentiation; at 2048 and 8192 bits it matched real keys). So 150 signatures naming a held 16384-bit key, the largest key-sync stores, cost about 165 ms of crypto; `policy.max_signatures` caps the count. Loading lua-openssl into each run's fresh Lua state adds 0.49 ms per signed request (luamonocypher: 0.08 ms), measured with a C loop that creates, uses and closes a `lua_State` per iteration with libssl already initialised, as in an nginx worker.

**Content codings.** Unencoded-Digest decodes in Lua, reached like hashing only through a good signature, but anyone holding one valid signature can replay it with any body, so the decoder's worst case is what counts. `lua lua/tests/coding/bench.lua` builds each path with `coding/bits.lua` and times it (best of three):

| Path | Lua 5.3.6, CRS image (arm64, Finch) | Lua 5.5.1, M1 Pro |
|---|---|---|
| Literals on fixed 8-bit codes | 7.0 MB/s | 9.0 MB/s |
| Literals on 15-bit codes (two table lookups each, the slowest bytes there are) | 3.6 MB/s | 4.9 MB/s |
| Matches of 258 at distance 1 (a bomb) | 22.4 MB/s | 33.6 MB/s |
| Stored blocks | 55.2 MB/s | 83.5 MB/s |
| The gzip CLI's `-6` output for 1 MiB of JSON-like text (ratio 5.5), CRC included: typical data | 9.5 MB/s | 13.8 MB/s |
| CRC-32 (gzip) / Adler-32 (zlib) | 31.1 / 45.8 MB/s | 45.6 / 77.9 MB/s |
| SHA-256 (`sha256.lua`), for scale | 4.2 MB/s | 6.1 MB/s |
| An empty fixed / stored block | 0.32 / 0.78 µs (1 / 3 slowest bytes) | 0.25 / 0.60 µs |
| An empty dynamic block (316 code lengths) | 191 µs (689 slowest bytes) | 122 µs |
| A dynamic block with the largest tables a code can force (32 subtables) | 247 µs (892 slowest bytes) | 154 µs |

So the worst a sender can make a decoded byte cost in the image is 3.6 MB/s plus the CRC, 3.2 MB/s: the default budget of 128 KiB is 40 ms there, the same order as the SHA-256 cap's 31 ms. The block charges come from the same table: an empty stored or fixed block costs at most 3 bytes' worth, charged 16; a dynamic block at most 892, charged 1024. Without them, a body of empty fixed blocks (1.25 bytes each) would cost about 3.4 s of CPU at the image's 12.5 MiB `SecRequestBodyLimit`, and one of empty dynamic blocks (168 bytes each) about 15 s, while producing nothing. Every symbol takes at most two table lookups (zlib's root and subtable scheme, 9-bit root), so no choice of code lengths is slower than the 15-bit row.

## Why lua-openssl

All four official CRS images link plain Lua 5.3, not LuaJIT. That rules out `lua-resty-openssl` and the rest of the FFI-based JOSE/JWT libraries. RSA and ECDSA need a real crypto library; plain Lua cannot do them at any useful speed.

- **lua-openssl** (chosen, 2026-10-03): a C binding to OpenSSL's EVP interface, MIT, maintained; it builds in the CRS image against the image's OpenSSL 3, and exposes `EVP_DigestVerify` (Ed25519, ECDSA, PKCS #1 v1.5) and `EVP_PKEY_CTX` controls (RSA-PSS parameters). Patching moves to the distribution's OpenSSL.
- **luamonocypher** (used until 2026-10-02): Ed25519 and SHA-512 only, unmaintained since 2022.
- **`luaossl`:** its `pkey:verify()` uses OpenSSL's legacy `EVP_VerifyFinal`, which cannot do Ed25519. The live error was `EVP_MD_CTX* expected, got string`; see [wahern/luaossl#188](https://github.com/wahern/luaossl/issues/188), open.
- **`luazen 0.16-1`:** the rock is out of sync with its repository and fails the RFC 9421 vector.
- **`lua-sodium` forks:** abandoned since 2014.

## History

This verifier was rebuilt on 2026-09-28/29 after an independent review of the first version.

That version failed both draft test vectors, never enforced `expires`, and attributed requests to unsigned `Signature-Agent` URLs. It read `@path` from the percent-decoded URI and let request-derived names reach `m.getvar`, which crashed a live nginx worker. Its example rule used `@eq`, which matches every status.

Each of those is now a named test or mutant above.

A second independent review of the rebuild (2026-09-30) found:

- **Absolute-form request lines:** the `@query` smuggling and Host-mismatch attacks above.
- **Non-ASCII component values:** RFC 9421 2.5 says these must be refused.
- **Key-store line endings:** a final bare CR, where the Lua and TypeScript parsers disagreed.
- **Locale-dependent Lua character classes.**
- **Key-sync:** log injection through a directory's `kid`, and a temp-file symlink race.
- **Test gaps:** skew boundaries, parameter types, and an oracle more lenient than the real module.

All are fixed and tested. One suggested fix, comparing `Host` with `SERVER_NAME`, was checked against libmodsecurity's source and rejected. `SERVER_NAME` is itself read from the `Host` header (`transaction.cc`), so the comparison could never differ.

A third, pre-publication review (2026-09-30) found:

- **Quadratic header trimming:** the pattern `^[ \t]*(.-)[ \t]*$` backtracks. One 8 KiB header of inner spaces cost 218 ms, so four such header lines cost about 0.9 s of CPU for one unauthenticated request. Now a linear scan, timed in `test_verify`, with a mutant.
- **The nginx guard matched one spelling of absolute-form.** Double spaces and methods with `-` or `_` got through and verified. The guard now refuses any signed non-origin-form target; three live cases pin the spellings.
- **Stale counts and one overclaim in these docs.**
- **Smaller items:** an unpinned base image; locale-dependent `%d`, `%x` and `string.lower`; the key store read before the `Signature` member was checked; undocumented millisecond `nbf`/`exp` handling; `@query-param` missing from "Not implemented".

Fixing those turned up one more, against the draft's text: a signature covering two `Signature-Agent` members (draft Appendix D.2, a remote browser covering its agent's member) was refused as `ambiguous-agent`. It is now attributed to the member keyed to its own label, as draft 5.2.1 says, and never to the other one.

A standards-compliance pass (2026-10-01) replaced choices that were stricter than the specifications without a security reason:

- **Structured fields:** the parser refused decimals and duplicate keys; RFC 9651 defines both. It now follows RFC 9651 throughout and passes the WG corpus.
- **Components:** `@query-param`, `;sf`, `;bs`, `@scheme` and `@request-target` were refused; RFC 9421 defines them. All are now implemented against the RFC's examples.
- **Outcomes the negative vectors exposed:** an `http` Signature-Agent was `unverified`, but draft 5.2.1's MUST makes it `invalid`. A signature over Content-Digest could verify without the body being checked, against RFC 9421 7.2.8; it is now `unverified`.

A fourth review of that pass (2026-10-01) found, all fixed and pinned:

- **Components x field size:** each covered component re-parsed its whole field, 2.65 s of CPU for one unauthenticated request at nginx's default header limits (table above).
- **`;bs` obs-fold regex:** quadratic on a long run of whitespace, the trim bug's class.
- **An absent Signature-Agent** was `invalid`; draft 4.3 makes it URL-less attribution, which is not implemented here: now `unverified/agent-absent`, matching NV-12.
- **Smaller:** `;key` on a field typed as a List or Item, the RFC's obs-fold example missing from the tests, stale RFC 8941 references, and doc claims about CI and counts.

RFC 9530 body digests (2026-10-01): signatures over Content-Digest, Repr-Digest and Unencoded-Digest are now decided in phase 2 against `REQUEST_BODY`, replacing `unverified/content-digest-unchecked`. `sha256.lua` is new; SHA-512 comes from the luamonocypher already shipped. Design facts checked in libmodsecurity's source before writing it: phase-2 rules never run when the body was not read (`processRequestBody` returns first), `REQUEST_BODY` is the raw body whatever the processor, `INBOUND_DATA_ERROR` marks a cut body, and `m.getvar("TX.x")` resolves without throwing.

A clause-by-clause requirements audit (2026-10-01) traced all 240 BCP 14 sentences of RFC 9421 (113), the WBA draft (83), RFC 9651 (29) and RFC 9530 (15) to code, tests or a stated reason. Fixed and pinned, each with a test and a mutant or a key-sync test:

- **Component identity:** duplicates were compared by their serialization, so `"d";key="a";sf` and `"d";sf;key="a"` both verified (RFC 9421 2: parameter order is not significant), and so did `"d";key="a"` beside `"d";key="a";sf` (2.1.2: a key is covered once).
- **HTAB in derived components:** accepted; the 2.5 ABNF allows only VCHAR and SP.
- **An empty `Host` port** (`example.com:`) was kept; RFC 3986 6.2.3 removes it.
- **Key-sync stored keys published with their private part** (`d`), and keys whose `alg` names another algorithm (RFC 9421 3.2 step 6.5).
- **Five RFC 8032 test keys were not refused** (draft 6.8). RFC 8032 TEST 1, which is also RFC 8037's example key, was the fixtures' "valid agent key"; the fixtures now use a key generated for them, whose private half was discarded.
- **Header order** was assumed, not shown; the live suite now proves it.

The audit's remaining items were choices, each set out with the case for and against in `CONFORMANCE.md`.

Following the text (2026-10-02). Every one of those choices was settled by doing what the specification says. Each change has a test, and the verifier changes a mutant:

- **Every signature is validated** (draft 5.2.2), with no cap by default; `tx.wba_agents` lists every verified directory.
- **URL-less verification** (draft 4.3): no `Signature-Agent` and a held key is `verified/url-less`, attributed to the key alone.
- **Orphan labels** (RFC 9421 4) are an error for every label, not only the one being verified.
- **`@query-param` spaces are `+`** (RFC 9421 2.2.8 step 2), not the `%20` of the RFC's example; the vectors are now `URLSearchParams` output, unchanged.
- **An explicit `:443`** in a Signature-Agent member is ignored (draft 5.5).
- **Unparsable signature or digest fields get 400** (RFC 9651 4.2, draft 5.4).
- **Signed requests over cleartext get 400** from nginx (draft 6.1). The live suite now sends every signed case over TLS, and checks that a signed cleartext request never reaches ModSecurity.

Every algorithm (2026-10-03). RFC 9421 3.3's algorithms that the draft allows, all but `hmac-sha256` (draft 6.4), replace Ed25519 alone:

- **lua-openssl replaces luamonocypher**, behind `crypto.lua`; SHA-512 for body digests comes from it too. The image test stage now runs every Lua suite against it, plus `test_crypto`, 1798 Wycheproof vectors over the five algorithms and the 10 `crypto.lua` mutants.

Lengths are exact per algorithm and key, so a DER-encoded ECDSA signature never reaches the crypto.

RFC 9530 as fully as a request verifier can (2026-10-03), built on a third parallel branch and merged after the two above. Each change has a test and a mutant:

- **Unencoded-Digest over coded bodies** (draft-ietf-httpbis-unencoded-digest-05 3, 5): `gzip`, `x-gzip` and `deflate` bodies are decoded, stacked codings last-applied first, by `coding.lua`, which replaced `unverified/digest-unsupported`. Decoding is budgeted (`max_decoded_body`, `max_decode_ratio`, block charges); a body that is not its coding is `invalid/bad-content-coding`; `br`, `zstd`, `compress` and unknown codings are `unverified/digest-coding-unsupported` (DESIGN.md, Not implemented).

Unencoded-Digest on a partial PUT, which was compared with the partial body, is now `unverified/digest-partial` like Repr-Digest.
